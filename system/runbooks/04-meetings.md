# 会议：从手机录音到可核对的纪要

前置：完成自己的同步与扩展 MCP，固定二进制导入入口。参考源码在 `production-reference/meeting/` 与 `meeting-bridge/`。本章涉及第三方付费转写；先让使用者确认账户、费用和允许处理的录音范围。

## 两个入口，一条处理队列

- **直接上传**：手机录音/文件分享 → 自己的 HTTPS 接收器。手机访问令牌只给自己的设备。
- **同步监听**：将音频放进约定的 Inbox → LiveSync 附件同步完整 → `inbox_listener.py` 通过二进制桥读取 → 接收器。

两路都按音频内容 SHA-256 识别同一任务，SQLite 保留状态。附件尚在增长时先等待；失败重启后沿原任务恢复，不能换文件名绕过去重再次计费。监听器首次启动的 seed 路径必须由使用者明确选择，避免把历史录音全量送去转写。

## 部署接线

1. 使用 Linux 独立服务账户，将接收器文件放到自己的 `/srv/wiki/meeting`，确认模块导入目录。创建独立 Python 虚拟环境，安装该目录 `requirements.txt`。同时安装确认目录的 `kb_dictionary_cache.py`、`kb_confirmed_dictionary.py`、`kb_tingwu_phrases.py` 到 `/opt/kb-confirm` 或可导入位置；它们是纪要词典/热词依赖，不是可省略的 UI 文件。服务模板见 `system/deploy/wiki-meeting.service.example`。SDK 提供阿里云请求；语音模型属于后续单独环境。
2. 将 `system/config/meeting.example.json` 复制到**仓库外的私有目录**，填写自己的听悟 AppKey、AccessKey、HTTPS 基址和 meeting 身份。示例占位符不是可用凭证。密钥文件只允许运行用户读取，不加入 Git。
3. `receiver.py --config <自己的配置>` 监听回环地址。用自己的反向代理仅开放接收器实际需要的上传、查询和签名音频路由；路由定义以 `receiver.py` 为准，不把工作目录或配置目录映射成静态目录。
4. 听悟服务需要能通过**限时签名 URL**读取这次音频；签名必须覆盖路径与有效期。链接泄露、过期和路径穿越均应拒绝；不能把整个音频目录设为公开。
5. 将 `meeting-import.mjs` 接到自己的 MCP 宿主，注册只接受固定 `job_id` 的 `import_meeting`。服务端读取已验证的任务清单并检查目录/文件哈希；调用方不能任意指定全库写入路径。
6. 配置 `inbox-audio-bridge.mjs` 的真实 Vault 二进制读取能力和挂载路径，再启动监听器。原生产脚本含 Linux/Docker 假设，不能直接当 Windows 后台任务。

`phone_token`、音频签名密钥、云服务 AccessKey、meeting MCP token 是四种不同用途，不要合并成同一把密钥。原系统还会读取已确认词典/听悟热词资源，详见确认手册；读取失败不能伪称已加载。

## 产物和事实来源

保留原录音、原始转写 JSON、完整转写和时间戳。纪要是派生材料；不能因为已有摘要就删掉完整正文。导入结果的 `.obsidian.json` 是导入回执，不等于内容已经被萃取到正式 Wiki。整理 Agent 再读取原文和旧页，走正常提交链。

字典纠错、发言人名字变化只更新派生展示。原始音频/原始识别结果不可覆盖。格式转换服务只对明确支持的格式提取正文；图片 OCR、音视频理解没有安装时应明确待处理，不能写一个空正文冒充完成。

## 最少验收

用取得授权的短测试录音逐项记录：上传成功 → 任务 ID → 听悟原始结果 → 完整转写有段落/时间 → 纪要 → MCP 导入回执 → 两端原件可打开。然后重复上传同一字节、重启接收器、模拟额度不足、附件未传完、签名过期、错误 meeting token，证明没有重复提交和越权。

仓库包含原接收器的单元测试；它们使用替身数据，**不会证明自己的云账户已开通或真实录音能成功转写**。真实费用、手机上传与模型结果要在自己的环境另验收。
