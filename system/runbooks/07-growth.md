# 知识自生长：让资料持续变成可更新的知识

“自生长”是持续接收、完整阅读、对照旧知识、补充主题、追问、核证、复查。它需要模型理解和程序保护共同完成，不能把定时摘要称为已经完成。

## 各角色怎样合作

- **查询**只读正式知识、时间线和原文；输出有来源与不确定性。需要保存回答时只能创建问答投稿。
- **整理**读来源全文/分段与旧页，按 `prepare → context_read → stage → commit → 回读` 工作。租约、原文/旧页/规则版本、完整阅读预算、事务恢复、索引和台账由程序强制检查。
- **确认**先检索已有知识，登记稳定问题。真实答复优先处理，但答复可能仍要与其他证据核对；草案不是用户事实。
- **巡检**分结构检查与内容检查。旧知识是否更新、时间是否正确、真实问题能否答对，要独立验证。来源存进去、读取过、提交过、语义通过、全库完成是不同状态。

规则细节和示例见 `docs/02`、`docs/03`、`docs/06`、`docs/08` 及三个业务 Skill。时间规则保留事件发生时间、原件时间、整理时间；没年份不能补年份，计划不能写成已发生。相同来源版本幂等处理，来源更新应刷新旧主题，不重复增加“新来源”计数。

## 调度和控制器

实际系统分为常驻文件监听、短间隔确定性服务、定时模型任务、独立控制器。**只用一套权威写入租约和一个控制器**。先查看使用者已有任务再安装，不能因为公开仓库多了例子就再创建一套 Bot。

参考的任务分工：

| 工作 | 节奏与限制 | 验收证据 |
|---|---|---|
| 新资料整理 | 每小时分批；普通来源预算、答复优先及长文续读由策略控制 | 唯一 source/version、提交 journal、更新页 |
| 结构巡检 | 每日或确定性定时器 | 路径/链接/台账/索引报告；不是语义通过 |
| 内容巡检 | 每周、到期复核 | 对照来源与旧页、需更正事项 |
| 固定问题验证 | 每月独立验证者 | 实际答案、引用、时间正确性；独立于 Chief 自测 |
| 问题/答复/身份/回执同步 | 短周期、单实例、可恢复 | 持久事件/ack/最终回执 |
| 日报与停顿报警 | 固定交付时间，独立于模型任务是否成功 | 报告回读、最新进度、失败/未知分开 |

这里列的是任务分工；实际读取到的服务定时配置见 [service-inventory.json](../service-inventory.json)。新环境先低频、低预算启用，保留使用者的时区、模型、开关、负责人和历史。每个日程必须明确“谁执行、什么权限、最大费用、何时暂停、如何回读”。

## Rakazo 与其他 Agent 平台

原控制器依赖 Rakazo 的数据库、租户上下文、队列和任务 API。自己的平台版本不一致时先适配，不直接在数据库里替换几个 ID 就运行。`WIKI_ROUTINE_ID`、`WIKI_SPACE_ID`、`WIKI_USER_ID`、日报/巡检 ID、看板 ID 必须是使用者自己的记录。

自动恢复默认关闭；`WIKI_WATCHDOG_APPROVED_AT` 与 `WIKI_ENABLE_AUTO_RECOVERY` 表示**新环境主人自己的授权**，不能继承作者历史授权。暂停、归档、人工维护优先于恢复；并发更新时停下回读。模型中继故障与知识文件同步故障分开诊断，不能“重新提交”来掩盖上游流中断。

其他平台可以替换调度/消息适配器，但要保留相同证据合同：真实 tool effect、固定租约、唯一来源版本、失败断点、暂停优先、预算和最终回执。Skill 文本不能替代程序权限。
