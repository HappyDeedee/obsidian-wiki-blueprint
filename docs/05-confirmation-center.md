# 确认中心：让主人只回答真正需要的问题

确认中心不是一张“AI 说已经解决”的表，而是一条可追溯的闭环。

```text
发现疑点 → 先回原文 → 必要时查公开资料 → 仍不能确定才问主人
    ↓                                               ↓
问题登记（稳定 ID + 版本）                   主人真实答复及出处
    ↓                                               ↓
卡片/待答 → 已收到投稿 → 核对编号/版本/来源 → 知识修复 → 最终回执 → 已入库
```

## 先查，再问

每个疑点保留原页、原句、冲突双方、已查范围、优先级。分成：

1. **需原文**：读原页、引用来源、关联主题、完整会议转写和用户自述。能核清就直接依据原文修，不问主人。
2. **需外部**：只查公开术语/政策/平台概念；有 web_search/web_fetch 才查，打开官方/原始页面，保存访问时间、1–3 句候选释义与网址。不要将私人材料发给公共搜索，也不直接写正式知识。
3. **需主人**：私人用法、记忆、意图或无法裁决的冲突，给可回答的题目、初步结论/2–3 个选项与出处。

可配置每轮最多 25 条，并受总时间/工具预算限制；没做完保留编号续跑。程序 hash、队列位置、模型错误属于运维，不转成向主人提问的知识疑点。

`trust` 可用“库内有原文 / 库内推断 / 有出处（外部） / 请你裁定”。公开释义有出处不等于私人含义已确认。草案另存 `external_draft`，兼容旧 `hark_draft` 名称也必须按草案处理，永不进入主人答复证据。

## 数据结构

问题最少有 `question_id/question_version/target_paths/source_versions/ask/options/evidence/status`。稳定 ID 跨批保留；改问题含义或关键证据就升 version，不按行号当身份。

答复最少有：`kind: confirmation-response`、问题 ID/版本、真实原话、answer_source、received_at、answer_id，以及可选 supersedes。确认中心应从认证会话记录作者，不能信任正文的 `user_confirmed:true`。

状态：`pending → received → verifying → adopted`；还可为 `needs_review/closed_unknown/superseded/rejected`。`adopted` 只在对应正式知识 commit 最终 PASS 且收尾完成后出现；附改动页与 commit_key。收到、排队、HTTP 200 或模型“完成”不等于采纳。

## 核证与幂等

- 先对照登记、题目版本、原页、原始来源和用户真实出处；旧版/跨题答复留待核，不套到新版。
- 同 ID + version + 规范化原话去重，仍保留原答复文件与关联。重复收到不再次计成功。
- supersedes 核同题同版与真实替代关系；循环、跨题和同时冲突不按 mtime 强行裁决。
- “不知道 / 保留未知并关闭”就是未知；关闭后不反复问同一问题，不补造答案。
- 事实核实后用 topic_repair 精确更新已有主题和登记，保留原页历史、答复来源与回执；不为每条答复生成来源摘要。
- 词义确认不证明业务行动已发生；发言人身份确认不证明其观点为真。
- 合并卡要包含主页、所有成员版本、保留差异、逐字证据、no_delete。用户同意不等于确认全部事实；冲突仍待核。完成后旧页重定向与备份保留，不删除原件。

## 最小可用界面：Markdown

本仓库参考版将问题放在 `90-Logs/待确认/questions/`，答复放在 Inbox。运行 demo 后可以在 Obsidian 直接看卡片与最终回执；不需要网页，也不暴露端口。

```powershell
python tools/wiki.py question --vault "../my-wiki-demo" --id "demo-extra" --target "20-Wiki/实体/演示项目.md" --ask "这项功能是计划还是已完成？"
python tools/wiki.py answer --vault "../my-wiki-demo" --id "demo-extra" --version 1 --text "仍是计划" --source "本地用户现场答复"
```

answer 只登记 received。后续 curator 核原文、提交修复，再用对应 commit 回执 resolve。真实来源的真实性由受信任操作者核查；本地 CLI 不提供用户登录证明。

## 如需和生产一样的网页入口

需另实现：用户登录、CSRF 防护、同源检查、输入转义、question version 乐观锁、原子答复投稿、审计、最终回执轮询、撤销/更正与未知关闭。建议独立后端只暴露“列本人问题 / 提交本题答复 / 查询本答复状态”，不让浏览器直接持 curator 或数据库密钥。

网页显示分三段：“已收到”“核验中/卡住原因”“已入库及页面链接”。同题过期版本返回冲突，不悄悄替换。音频身份卡额外需要私有试听授权、逐场 speaker 范围和撤销机制；不把声音文件或声纹向量放到公共仓库。

**本仓库不附原私人网页服务源码或声纹服务。** 完整蓝图、字段与验收用例已给出；搭建 Agent 必须把这项列为待实现，不可声称网页已安装。

## 调度与时效

每日先处理答复，再会议、日记、其他资料。答复不挤占普通来源每轮上限，但仍受总资源预算和单 writer 限制。可按本地时区设截止点；超过 24 小时仍无核证/采纳回执时巡检报警，给 ID、接收时间、当前状态与卡点。没有待答不新建第二套周提问机器人。
