# 验收：怎样知道真能用

## 仓库自动测试

在仓库根目录：`python -m unittest discover -s tests -v` 和 `python tools/check_public.py`。本地参考程序不调用任何真实 MCP、云服务或模型。测试用例是虚构材料。

验收三层：

1. **程序结构**：版本、证据字面匹配、journal、备份、回读与幂等。
2. **知识语义**：原文的关键主张是否准确写入主题、历史是否保留、计划是否误写已发生。
3. **实际使用**：正常 Agent 入口能否从知识与原文回答，引用是否真实；独立设备是否同步。

第一层 PASS 不能替代后两层。

## 必做测试矩阵

| 场景 | 预期 |
|---|---|
| 两份同主题来源 | 优先更新同页，不机械建两个概念 |
| 同来源同版本重放 | 原回执 reused，无重复来源成功数 |
| 来源内容变化 | refresh；旧计划失效，不能沿旧 hash 写 |
| prepare 后旧页被人工编辑 | commit 拒绝；不得覆盖人工变化 |
| 两个 writer | 只有一个获准；另一个 BUSY |
| 写完一页后崩溃 | 同 token 同参数恢复；不另起事务补成功 |
| 只 stage 未读完全 | 不允许最终成功，不推进完成断点 |
| 引文不是逐字原文 | 拒绝，不把模型改写当 evidence |
| 查询身份调用写工具 | 服务端拒绝，不是“提示它别写” |
| 投稿覆盖已存在文件 | 原子拒绝，旧文件不变 |
| `../`、绝对路径、symlink/ADS | 拒绝，不能越出库 |
| 旧 question_version 答复 | 保留待核/拒绝，不套用新版 |
| 草案伪装 user_confirmed | 不采纳，不写正式知识 |
| 重复答复、supersedes 循环 | 去重/待核，不重复变更 |
| 收到答复但 commit 失败 | 显示 received/卡点，不显示 adopted |
| 不知道并关闭 | 保留未知，不反复问 |
| 有权采纳合并 | 保留差异、备份及旧页重定向，不删源 |
| 缺年份或只有文件时间 | 不补事件年，不补 source_date |
| 纪要与完整转写数字不同 | 回原转写，标差异，不信自动摘要 |
| 计划被写成上线 | 语义验收不通过，即使结构 PASS |
| 检索无命中/分页未查全 | 仅说明已查范围，不能断言不存在 |
| 导入图片未 OCR | 标未读，不能算空源或完成 |
| 生成成果再次被发现 | 排除，不形成循环来源 |
| 到复核日但无新证据 | 记录待复核，不自动延期或整页作废 |

其中哪些由参考实现自动测，见 tests；其余属于服务器适配器/模型/同步验收，必须另跑，不能复制表格就写通过。

## 新用户的语义样本

使用虚构材料：原文“演示项目计划下周测试，预算为未知”；知识应为 planned/预算未知。用户确认“尚未测试”；核证后精确更新，并保留旧页和答复出处。问“是否已经上线、预算是多少”，正确回答仍是未核实上线/预算未知，不能编数或把计划当事实。

再加一份可靠来源证明“测试已完成但未上线”，应更新同一主题、保留历史、区分测试与上线。请让正常查询 Agent 实际回答并检查其工具日志和引用，不看它是否口头说“成功”。

## 报告格式

记录日期、环境、命令/工具、输入/输出 hash、回执、当前结果、实际 read_paths/unread_paths、未通过与不适用。公开报告仅用虚构样本，生产报告与连接数据保留私人目录。不要把测试样本、源文件数量或安装成功当作全库完成。
